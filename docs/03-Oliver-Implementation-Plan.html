0From build-plan to executable plan

02-Oliver-Azure-Build-Plan answered what to build and in what order — six phases, each with a hard exit test. This document answers how each piece actually gets delivered: the numbered steps, who does each part, what proves it works, and when it ships. The phases and their exit tests are unchanged; here they are decomposed into 22 numbered steps, and every step runs the same disciplined cycle — plan, build, test, validate, document, deploy.

The neat part: we apply Oliver's own agentic philosophy to building Oliver. Just as the run-time mesh has agents for assessment and operations, the build gets a small delivery squad of four agents that own the plan-build-test-document loop. The same governance ethos — evidence-mandatory, human-in-the-loop on irreversible calls, auditable by construction — carries straight into how the system is constructed.

The one-line shift: the six phases stay the same; this plan makes them executable — 22 steps, each with an Implement / Test / Validate / Deploy contract and a named owner.

1The delivery squad — four new agents

These are build-time agents — distinct from the 17 run-time mesh agents in doc 01. They construct, prove, and ship the system. Each maps to one facet of the request: build, test, validate, deploy — with the Planner owning the gates and the Documentor recording every step.

P

Planner · NEW

Validation & sequencing

Breaks the phases into dependency-aware steps, defines each step's exit gate, and owns validation: a step is only "done" when its gate passes. Re-plans the moment a test fails — it never lets failed work move forward.

Guard: every step has an explicit, testable exit gate; no work starts before its dependencies are met; failures loop back, they don't get waved through.
B

Builder · NEW

Implementation

Does the implementation: provisions Azure resources via IaC, writes the Function and agent code, and wires the integrations (Graph, Service Bus, Cosmos, SAP). Turns a planned step into running infrastructure and code.

Guard: infrastructure-as-code only — no manual portal clicks; managed identity everywhere; no secrets in code or config.
T

Tester · NEW

Testing & assurance

Owns testing at every level — unit, integration, shadow-diff vs Power Automate, load, security, compliance. Produces the evidence the Planner's gate consumes, and blocks promotion until the tests are green.

Guard: no promotion without passing tests and the evidence attached; shadow-parity must hold before any cutover.
D

Documentor · NEW

Record of truth

Captures the runbooks, architecture decisions (ADRs), the Cosmos registry schema, API docs, and the event taxonomy — and keeps docs 01 / 02 / 03 in sync as the build teaches us things.

Guard: every shipped step leaves an artifact-of-record; docs are updated before a step is called Done — not after.
Why a squad, not a checklist: the four roles are a separation of concerns — the one who builds is not the one who decides it passed (Builder ≠ Planner gate), and nothing ships undocumented. That is the same "govern the governor" discipline doc 01 applies to the run-time mesh, turned inward onto the build itself.

2The delivery loop — every step runs this cycle

Each of the 22 steps moves clockwise through the same loop. A failed gate doesn't stop the project — it loops back to the Planner, who re-sequences and the cycle repeats.

Plan→ Build→ Test→ Validate (gate)→ Document→ Deploy

↺ Gate fails → back to Plan (re-sequence & retry). Gate passes → Document → Deploy → next step.

  • Plan — Planner confirms dependencies are met and restates the step's exit gate.
  • Build — Builder provisions + codes the step (IaC, Functions, wiring).
  • Test — Tester runs the level(s) of tests that apply to this step.
  • Validate — Planner checks the evidence against the gate; pass or loop back.
  • Document — Documentor records the artifact-of-record and updates the living docs.
  • Deploy — promote through dev → test → prod behind the CI/CD gates in §12.

12Environments, CI/CD & Definition of Done

Three environments

  • dev — Builder's workspace; fast iteration, synthetic data.
  • test — integration + shadow-run live here; mirrors prod topology; the diff harness lives here.
  • prod — real submitters; reached only after the gates pass. Same IaC templates as test.

CI/CD promotion gates

  • PR → lint + unit + IaC what-if must pass.
  • dev→test → integration tests green.
  • test→prod → shadow-parity + security + compliance green, and Planner sign-off.
  • Irreversible prod changes (cutover, weight updates) → HITL approval, never automated.

Definition of Done — a step is Done only when…

  1. Builder implemented it as IaC + code, no manual steps, no secrets.
  2. Tester has green tests at the levels that apply, with evidence attached.
  3. Planner confirms the exit gate passed (or loops it back).
  4. Documentor left the artifact-of-record and updated docs 01/02/03.
  5. It is deployed to the right environment behind the right control.
Sign-off rule: phase-exit steps (3, 9, 13, 16, 18, 20) and both cutover steps (21, 22) require an explicit human sign-off in the Human Console — automate the prep, never the judgement.
Decisions to lock before step 5: the canonical scoring model (v3.0 0–100 / 5-dim vs tracker 0–200 / 4-dim) must be resolved — it freezes the Registrar schema that steps 5 onward key off. Also start the SAP read-access request now (needed in step 17, longest lead) and decide mailbox deliverability ownership (step 4).

13Appendix — delivery-agent system prompts (click to expand)

Draft scaffolds for the four build-time agents, in the same ROLE/GOAL/INPUT/DO/OUT/GUARD format as the run-time mesh prompts in doc 01. These encode the delivery discipline: gate-before-done, IaC-only, evidence-mandatory tests, and document-before-Done.

NEWPlannersequencing & validation gates+ 
ROLE  You are Planner, the delivery agent that sequences and validates Oliver's own build.
GOAL  Turn each phase into dependency-aware steps and guarantee none ships without passing its gate.
INPUT The six-phase build plan, the current step, its dependencies, and the Tester's evidence.
DO    Confirm dependencies are met before a step starts. Define a single, testable exit gate per step.
      On Validate, compare the Tester's evidence to the gate: pass → release to Document; fail → re-sequence
      and loop the step back to Build. Hold the phase-exit and cutover sign-offs for a human.
OUT   {step, dependencies_met, exit_gate, verdict: pass|loop_back, next}.
GUARD Every step has one explicit, testable gate. No work starts with unmet dependencies. A failed gate is
      never waved through — it re-plans. Irreversible steps require human sign-off.
NEWBuilderimplementation — IaC, Functions, wiring+ 
ROLE  You are Builder, the delivery agent that implements each step.
GOAL  Provision the Azure resources and write the code/integration a step requires — reproducibly.
INPUT A planned step with its exit gate and the target environment (dev/test/prod).
DO    Provision via Bicep/Terraform; write Function & agent code; wire integrations (Graph, Service Bus,
      Cosmos, AI Search, SAP via APIM). Reuse v3.0 prompts verbatim where the step ports an existing agent.
OUT   {iac_changes, code, wiring, env, ready_for_test}.
GUARD Infrastructure-as-code only — no manual portal clicks. Managed identity everywhere; no secret in code
      or config. Build to the gate, not beyond it — no gold-plating.
NEWTestertesting & promotion assurance+ 
ROLE  You are Tester, the delivery agent that proves each step works.
GOAL  Produce the evidence the Planner's gate needs, at the right level(s) for the step.
INPUT The built step and its exit gate.
DO    Run the applicable levels: unit (golden fixtures, evidence-mandatory), integration, shadow-diff vs
      Power Automate, sandbox/UAT, load/performance (<24h decision), security, compliance. Attach results.
OUT   {levels_run, results, pass|fail, evidence_refs, divergences[]}.
GUARD No promotion without passing tests AND attached evidence. Shadow-parity must hold before any cutover.
      A real telemetry feed only — never assume green.
NEWDocumentorartifacts-of-record & living docs+ 
ROLE  You are Documentor, the delivery agent that records how Oliver is built.
GOAL  Leave a durable artifact for every shipped step and keep docs 01/02/03 in sync.
INPUT A validated step plus its build & test outputs.
DO    Write the runbook / ADR / schema / API doc / event-taxonomy entry the step produced. Update the
      registry schema, the event taxonomy, and the living planning docs as the build teaches us things.
OUT   {artifact_of_record, docs_updated[], decision_log_entry}.
GUARD Every shipped step leaves an artifact-of-record. Docs are updated BEFORE a step is called Done —
      never after. No undocumented production change.
