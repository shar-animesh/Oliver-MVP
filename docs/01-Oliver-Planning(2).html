0The thesis in one paragraph

Oliver today is a point-in-time assessor: a submission arrives, ten agents score it, it gets a DI stage and a coaching email. That is a gate — a moment. AI lifecycle management is a continuum. The opportunity is to keep the gate as the entry point but extend the same multi-agent pattern across the whole life of a pilot — sensing ideas, coaching them between gates, monitoring deployed models, and proving the value actually landed. Concretely: keep the 10 agents, add a living registry as shared memory, add an operations & assurance cluster for live pilots, and put an orchestrator + event bus underneath so the system becomes continuous instead of one-shot.

The one-line shift: Oliver stops answering "should this idea pass the gate?" and starts answering "is every AI initiative in our portfolio moving, healthy, compliant, and delivering — right now?"

1Where Oliver is today — the stage-gating agent

Grounded in the AI Pilot Stage Gate Evaluation Protocol v3.0 (System: Oliver — Multi-Agent AI Pilot Assessment).

Oliver v3.0 is a 10-agent assessment pipeline with a deliberate design principle — "enable ideas to succeed, not gatekeep them out; financial rigour enters progressively." It scores on a unified 0–100 scale, applies stage-adaptive weights (idea quality dominates at DI1–2; business impact & execution gain weight at DI3–5), and a low DocGuard score (>30 to enter) routes to a coaching rejection rather than a hard no.

What's already strong and worth preserving: evidence-mandatory scoring, a coaching ethos (IdeaCoach), a human-in-the-loop endpoint, and an audit trail by design. These are exactly the properties a lifecycle system needs — Oliver was built on the right foundations.

Source: RAND (2024) — AI projects fail at roughly double the rate of conventional software delivery. The gap is not bad luck; it is structural. The five most-cited root causes — misunderstood intent, missing/poor data, chasing the latest tech over the problem, inadequate infrastructure, and problems too hard for current AI — are all things a one-shot intake gate cannot catch on its own.

Five structural differences (and why a gate alone can't manage them)

DimensionTraditional digital / SDLCAI initiative / ADLC
Behaviour Deterministic — same input, same output; testable against a spec Probabilistic — outputs are distributions; “correct” is statistical, can be confidently wrong
What it depends on Code quality & logic Data quality, freshness & representativeness — a data-engineering problem first
Deployment The finish line — ship and maintain The starting line — performance only becomes real, and observable, in production
Over time Stable until requirements change Degrades on its own — data & concept drift erode accuracy without any code change
Definition of done Meets requirements once Continuously meets a threshold (e.g. SLO ≥80%, bias <10%) and proves value landed

SDLC→ADLC framing synthesised from current MLOps / AI-lifecycle literature (Talentica, 2026; industry MLOps practice). The MIT finding is sharper still: the divide isn’t model quality — it’s a “learning gap.” Systems that don’t retain feedback, adapt, and improve in production stall in “pilot purgatory,” while the few that close the loop capture the value. McKinsey similarly finds the 16–30% productivity gains accrue to teams that treat AI as a collaborator to be coached over time — not a tool to be shipped once.

The throughline: every one of these differences plays out after the gate — in production, over time, against drifting data. A point-in-time assessor is necessary but structurally insufficient. The thing that manages a probabilistic, data-dependent, self-degrading, value-on-promise asset is a continuous lifecycle — which is exactly what the mesh adds.

3The core insight — a gate is a moment, a lifecycle is a continuum

Oliver as a stage-gate (today)

  • Reactive — waits for a submission to arrive
  • Point-in-time — scores once, then goes quiet
  • Stateless — the spreadsheet tracker is a manual snapshot
  • Intake-only — nothing happens between gates or after deployment
  • Answers: "did this idea pass?"

Oliver as a lifecycle mesh (target)

  • Proactive — senses and harvests candidate ideas
  • Continuous — re-assesses, nudges, and monitors over time
  • Stateful — a living registry is the single source of truth
  • End-to-end — coaches between gates, watches deployed models, tracks value
  • Answers: "is the whole portfolio healthy and delivering?"

The good news: most of the existing agents generalise from a one-shot role to a continuous one. We don't rebuild Oliver — we extend the pattern and add the missing planes.

7The behaviors the mesh must run — managing the portfolio, not just the gate

A lifecycle system is defined by what it does between and after gates. These behaviors are the point of the whole exercise — each is an event-driven policy, not a manual chore, and each already has a home in the architecture above.

Every pilot moves through live states — not a single pass

Activemoving on cadence → Stalledno movement → escalate Fail-fastbreach → No-Go Stellarexemplary → replicate Drifteddecay → upgrade → Decommissioned / Retired

The Registrar holds each pilot's current state; the Conductor fires the transition when a trigger event occurs; the Human Console is where a person confirms the irreversible ones (kill, scale, retire).

⛳Escalation for stagnated pilots

A pilot that hasn't advanced a gate within its expected window gets surfaced — owner first, then sponsor — before it quietly dies in “pilot purgatory.”

Trigger: days-in-stage > SLA · Runs on: Pacer detects → Conductor escalates → Herald notifies

📈Trend evaluation across submissions

Mine the whole intake stream for patterns: recurring gaps (e.g. governance always weakest), tech clusters, which problem types keep failing — so the funnel itself gets smarter.

Trigger: scheduled / on-submission · Runs on: Verdict as portfolio brain over the Registrar

🔔Reminders to advance pilots

Proactive nudges with a concrete next action and a “days-to-next-gate” countdown — the tracker already computes this; here it becomes an automatic prompt, not a spreadsheet column.

Trigger: approaching gate / idle owner · Runs on: Pacer + Herald digests

⭐Identification of stellar pilots

Auto-flag exemplary performers (high score + realized value + healthy SLOs) for fast-track, sponsor visibility, and replication to adjacent teams.

Trigger: score + realized-value thresholds · Runs on: Verdict + Realizer → Connector replicates

🛑Fail-fast mode

Extend the protocol's existing automatic No-Go (below 70%) into live operation: a pilot that breaches its SLO or stalls past threshold is recommended for a clean, evidence-backed kill — fast, not lingering.

Trigger: SLO breach / score floor / stall · Runs on: Sentinel + StageMaster → Human Console confirms

♻️Decommissioning & upgrading

Retire models that have drifted or been superseded; route others to a versioned upgrade. The pilot's end-state is recorded — nothing just disappears.

Trigger: drift / obsolescence / new version · Runs on: Sentinel detects → Conductor routes → Registrar records

🧬Synthesizing — the self-improving loop

The capstone behavior: learn which early signals actually predicted DI5 success or failure, and feed that back into the scoring weights. The portfolio's own history becomes training data for better gating — closing exactly the “learning gap” the MIT research identifies as the difference between value and pilot purgatory.

Trigger: pilot reaches terminal state (scaled / killed / retired) · Runs on: Verdict + Realizer feed back into scoring via the Registrar

Note on sequencing: these don't all arrive at once. Reminders, escalation and trend-mining ride on agents we already have (Pacer, Verdict, Herald) — they're Horizon 1–2. Fail-fast, decommissioning and synthesis depend on the Operations plane and the event bus — Horizon 2–3. The roadmap below sequences them.

9Design principles to hold onto

  • Single source of truth. One registry; agents collaborate through shared state, not copies.
  • Event-driven, not batch. A gate decision, an SLO breach, a drift alert — all are events.
  • Stage-adaptive everything. Weights already shift by DI stage; generalise that across the mesh.
  • Human-in-the-loop at decisions. Keep Oliver's existing review step; automate the prep, not the judgement.
  • Auditable by construction. Every score & decision logged — the framework already requires it.
  • Enable, don't gatekeep. Carry the v3.0 coaching ethos across the whole lifecycle.

10Open questions & risks to resolve early

TopicThe issue
Scoring model mismatch Protocol v3.0 uses a 0–100 scale + 5 dimensions (Idea Completeness, Idea Quality, Strategic/Business, Technical, Execution). The tracker & the MeetForge example use 0–200 + 4 dimensions (Documentation, Business Impact, Technical Readiness, Execution). Pick one canonical model before building the Registrar — everything downstream depends on it.
State store Where does the live registry live — Dataverse, a SharePoint list, a database? Decides integration effort and who owns it.
Monitoring data access Sentinel & Realizer need telemetry from deployed models and business systems (SAP PM/EWM/S4HANA appear across the tracker). Access & integration is the hard part.
Human-in-the-loop load More automation = more decisions surfaced. Design the console so reviewers get a prioritised queue, not a flood.
Trust & adoption Submitters must trust agent scores. Keep evidence mandatory; make reasoning transparent.
Governing the governor Oliver is an AI that gates AI pilots — it needs its own governance & bias review. Don't exempt the assessor.

11Suggested next steps

  1. Agree the canonical scoring/data model (reconcile v2.0 ↔ v3.0) — the prerequisite for everything.
  2. Stand up the Registrar as the live single source of truth and migrate the 20 existing pilots out of the spreadsheet.
  3. Pilot the Operations plane on 1–2 live DI3 pilots — e.g. Document Processing Automation and Logistics Route Optimizer (your exemplary-rated ones) — to prove the value loop closes.
  4. Define the event model + a Conductor MVP so the mesh can react rather than re-run.
  5. Draft Oliver's own governance charter (AI governing AI).

12Appendix — agent system prompts (click to expand)

Draft starting points — one per agent, grouped by plane. These are scaffolds to argue with, not final prompts; they encode the protocol's non-negotiables (evidence-mandatory scoring, the 0–100 scale, stage-adaptive weights, human-in-the-loop, an audit trail). Click any agent to reveal its prompt.

①Sensing & Intake
Get the right ideas in.
NEWScoutharvests candidate ideas+ 
ROLE  You are Scout, a sensing agent for Siemens Energy TI's AI-pilot funnel.
GOAL  Surface candidate AI use-cases before anyone fills in a submission form.
INPUT Teams channels, email threads, idea boards and project notes you are granted access to.
DO    Detect a real signal = a pain point + an available data source + a willing owner. Draft a
      one-line opportunity with a confidence score (0–100). Deduplicate against the Registrar.
OUT   Candidate record {title, problem, sponsor?, signal_strength, evidence_links} → Registrar as "Sensed".
GUARD Never invent a sponsor or a metric. You flag, you do not decide. Respect channel privacy scopes.
EXISTINGDocGuardcompleteness gate (>30 to enter)+ 
ROLE  You are DocGuard, the intake completeness gate.
GOAL  Decide whether a submission is complete enough to be assessed at all.
INPUT The raw submission (idea, value claim, tech approach, owner).
DO    Score completeness 0–100 across required fields. Below 30 → do not pass on; return the exact
      list of what is missing so the submitter can fix it.
OUT   {completeness_score, missing_fields[], pass}.
GUARD Completeness is not quality. You judge only whether enough is present to evaluate — never the merit.
②Assessment
Score & stage — the current Oliver core.
EXISTINGIdeaPulseidea quality & problem fit+ 
ROLE  IdeaPulse — assess idea quality and problem fit on the unified 0–100 scale.
DO    Is the problem real, specific and worth solving? Is the approach a fit? Every point of score
      must cite evidence drawn from the submission.
OUT   {idea_quality_score, problem_fit, strengths[], gaps[], evidence[]}.
GUARD Evidence mandatory — no evidence, no score. Enable, don't gatekeep: frame gaps as fixable.
EXISTINGValuePulsestrategic → financial value+ 
ROLE  ValuePulse — translate the idea into strategic and financial value.
DO    Check against thresholds: ROI ≥15%, cost savings ≥€100k/yr, efficiency gain ≥20%, ≥30 viable
      users. Weight rises at DI3–DI5.
OUT   {value_score, roi_claim, savings_claim, adoption_estimate, evidence[]}.
GUARD Distinguish projected from proven. Record every claim so Realizer can verify it later.
EXISTINGTechScopetechnical feasibility & data readiness+ 
ROLE  TechScope — technical feasibility and data readiness.
DO    Is it buildable? Assess data availability/quality, model approach, integration surface
      (Teams / Jira / SAP PM / EWM / S4HANA) and infrastructure.
OUT   {tech_score, data_readiness, key_risks[], evidence[]}.
GUARD Poor data is the #1 cause of AI failure — score data readiness explicitly, never assume it.
EXISTINGPathFinderexecution readiness+ 
ROLE  PathFinder — execution readiness.
DO    Assess sponsor, core team, budget, plan and governance. Stage-adaptive: weight rises at DI3–DI5.
OUT   {execution_score, sponsor?, team?, budget_status, gaps[]}.
GUARD Express what's missing as actions with owners — don't just deduct points.
EXISTINGVerdictconsolidate + portfolio brain+ 
ROLE  Verdict — consolidation and consistency.
DO    Merge dimension scores into one 0–100 result using stage-adaptive weights; flag contradictions
      across agents. In lifecycle mode, also mine cross-pilot patterns and flag stellar / stalling pilots.
OUT   {overall_score, consistency_flags[], portfolio_signals[]}.
GUARD ≥70% is the pass bar; below recommends a No-Go — never an automatic kill. A human confirms.
EXISTINGStageMasterDI assignment → state machine+ 
ROLE  StageMaster — the lifecycle state machine.
DO    Assign DI1–DI5 from the consolidated score and evidence. In lifecycle mode, hold each pilot's
      live state (Active / Stalled / Fail-fast / Stellar / Drifted / Retired) and emit a transition event.
OUT   {di_stage, state, transition_event?}.
GUARD A stage is a claim about evidence, not ambition. Every transition is logged.
